# Правила работы над проектом

Проект: Android-приложение «Календарь самогонщика» на Flutter. Язык интерфейса, документации и коммитов — русский.

## Обязательный цикл изменения

1. Внести изменение (код, контент, документация).
2. Поднять `VERSION` по SemVer:
   - `MAJOR` — несовместимое изменение схемы БД или ломающий UX-передел;
   - `MINOR` — новая функциональность;
   - `PATCH` — исправления, тексты, документация.
3. Добавить запись в `CHANGELOG.md` (секция версии, дата, что и зачем).
4. Проверить:
   - `flutter analyze` — без новых ошибок;
   - `flutter test` — тесты зелёные;
   - миграции БД проверяются на чистой установке и на базе предыдущей версии.
5. Собрать APK (`flutter build apk --release`) — приложение должно ставиться и запускаться.
6. Коммит осмысленный, на русском: `feat:`, `fix:`, `docs:`, `chore:` + суть.

## Что не коммитим

- `build/`, `.dart_tool/`, `.gradle/`, `*.apk`, `*.aab`, `*.jks`, `key.properties`.
- Локальные БД, бэкапы пользователя, логи, временные файлы.
- Личные данные, реальные адреса устройств, пароли.

## Контент

- Рецепты и справочники — данные, а не код: хранятся в ассетах/БД и правятся без переписывания логики.
- Каждый рецепт имеет источник и пометку «проверен на практике».
- Чужие тексты не копируем: переписываем своими словами.
- Тематика алкоголя: без призывов к продаже, с рейтингом 18+, безопасность (метанол, огонь, вентиляция) — обязательный раздел.

## Особенности Flutter 3.50

`package:flutter/material.dart` помечен deprecated в пользу `package:material_ui/material_ui.dart`. **Мы остаёмся на `flutter/material`** и подавляем `deprecated_member_use` в `analysis_options.yaml`, потому что:

- `material_ui` — полная копия Material со своим классом `ThemeData`, несовместимым с третьими пакетами (`fl_chart`, `flutter_local_notifications`, `file_picker`), которые импортируют `flutter/material`;
- смешивание даёт виджеты, отрисованные дефолтной темой, а не нашей;
- `flutter/material` не удалён и продолжит работать, пока экосистема не переедет.

Когда переезжать: когда пакеты, которые мы используем, начнут экспортировать `material_ui`. Тогда меняем импорты одним проходом.

Ещё одна ловушка: у drift есть собственный класс `Batch`. Наш сгенерированный класс партии тоже называется `Batch` (`@DataClassName('Batch')`), поэтому в файлах, импортирующих drift, нужен `hide Batch`.

## Архитектура

- Оффлайн-первый, без аккаунта и телеметрии.
- Слои: `data` (drift, репозитории) → `domain` (модели, расчёты) → `ui` (экраны, виджеты).
- Состояние — не внешний state-менеджер, а `StreamBuilder` поверх drift-стримов и `AppScope` (InheritedWidget) для доступа к базе и сервисам. Меньше зависимостей — меньше платформенных сюрпризов на iOS.
- Расчёты (калькуляторы) — чистые функции с тестами, без зависимости от UI.
- Любая новая зависимость — только с обоснованием в CHANGELOG.

## Верстка форм

Отступы в формах не задаются «на месте» — они живут в `lib/widgets/form_fields.dart` (`FormSpacing`) и применяются через `FormNumberField` / `FormSectionTitle`. Причина: у outlined-поля плавающая подпись находится **выше** рамки, поэтому «нормальные» 8–12 px между полями визуально превращаются в слипание. Рабочие значения:

| Что | dp |
|---|---|
| Поле → поле | 18 |
| Заголовок секции → поле | 12 |
| Чипы → поле | 20 |
| Между секциями | 30 |
| Поле → подсказка под ним | 6 |

Подсказки (норма дозы, температурная поправка) рендерятся **внутри** `FormNumberField` через параметр `hint`, а не отдельным виджетом — иначе отступ под полем удваивается.

## Тесты

- Калькуляторы — юнит-тесты обязательно (формулы проверяем на известных примерах).
- Генерация событий из рецепта — юнит-тесты на даты и повторяемость.
- Критичные сценарии — интеграционные тесты на БД (создание партии, миграция, бэкап/восстановление).
