# Календарь самогонщика — план проекта

Android-приложение на Flutter: рецепты, партии, календарь процессов (брага → перегон → настойка → выдержка), учёт тары и дегустаций.

Статус: **этап планирования**, кода ещё нет. Документ — рабочая база, по нему режем объём на MVP.

## 1. Идея и позиционирование

Приложение не «ещё один справочник рецептов», а **журнал процессов с календарём**: ты заводишь партию по рецепту, приложение само раскладывает её на события (поставить брагу → проверить плотность → снять с осадка → перегон → залить в бочку → первая дегустация → готово к розливу) и напоминает, что делать сегодня.

Три вещи, которых нет у существующих решений (Broover, StillLog, Brewfather — все англоязычные и/или заточены под пиво):

1. **Русский язык и русская школа** — сахарная брага, КОДИ/ГМ, спирт-сырец, «головы/тело/хвосты», настойки и наливки (хреновуха, клюквовка, кедровка), щепа вместо бочки. Терминология та, которой реально пользуются.
2. **Календарь как главный экран**, а не журнал задним числом. Напоминания: «взболтать настойку», «долить бочку», «снять с осадка», «дегустация через месяц».
3. **Связка с собственной колонной** — у нас есть Smart-Column-S3 с HTTP API (`/api/history`, `/api/process/*`, `/api/settings/fermentation`): приложение может подтягивать реальные перегонки и температуру брожения, а не требовать ручного ввода.

Смотрел, что предлагают конкуренты, чтобы не изобретать заново:

| **Brewfather** | мощный инструмент для пива: рецепты, партии, инвентарь, оборудование, облако | пивная логика, подписка, тяжёлый для винокурения |

Вывод: рынок разорван на две половины — «калькуляторы/справочники» и «журналы». Связки «календарь + партия + русская терминология» на Android нет. Наша ниша — планировщик, который сам строит расписание из рецепта.

## 3. Что хранит приложение (сущности)

- **Рецепт** — шаблон: тип (брага / дистиллят / настойка / ликёр / выдержка / джин / ректификация), состав, шаги с длительностями и температурами, ожидаемый выход, источник (книга, форум, свой).
- **Партия (batch)** — конкретное воплощение рецепта: дата старта, объём, ёмкость, статус, родительская партия (брага → спирт-сырец → сортировка → настойка). Цепочка «от сахара до бутылки» прослеживается целиком.
- **Событие** — плановая или фактическая точка процесса, основа календаря и напоминаний.
- **Замер** — плотность/сахар/Brix, температура, крепость, кислотность, pH. Строит график брожения и «когда уже готово».
- **Перегонка** — прогон с фракциями: голова/тело/хвост, объём и крепость каждой банки, температура в кубе, скорость отбора.
- **Ёмкость/тара** — бочка (объём, обжиг, степень обугливания), бутыль, нерж, банка, бутылка. Кто в ней стоит и сколько.
- **Выдержка** — партия в бочке/на щепе: дата закладки, план, доливки, расчёт доли ангела, график дегустаций.
- **Дегустация** — оценка, аромат/вкус/послевкусие, что менять в следующий раз, фото.
- **Оборудование** — аппарат (пот-стилл, колонна, НБК), куб, мощность, датчики, адрес Smart-Column-S3.
- **Ингредиент** — справочник: сахар, солод, ферменты, дрожжи, специи, ягоды, с их нормами расхода.

Подробная схема — `docs/DATA_MODEL.md`.

## 4. Экраны (обзор)

Нижняя навигация из 5 пунктов:

1. **Сегодня** — задачи на сегодня и просроченные, активные партии с прогрессом, «скоро готово».
2. **Календарь** — месяц/неделя/список, фильтры по типу процесса, цветовые метки.
3. **Партии** — список с фильтрами по статусу, поиск, быстрый старт новой партии.
4. **Рецепты** — каталог встроенных + свои, поиск, избранное, масштабирование под свой объём.
5. **Ещё** — калькуляторы, склад/погреб, дегустации, оборудование, справочник, настройки.

Детально с состояниями — `docs/UX.md`.

Целевые платформы: **Android (основная) и iOS (закладываем сразу)**. Каркас уже мультиплатформенный: `app/android/` и `app/ios/` созданы, вся логика — в общем Dart-коде, платформенные различия только в уведомлениях, файлах и виджетах.

Предполагаемые зависимости (все — с поддержкой обеих платформ):

- **БД**: `drift` (SQLite, реактивные запросы, миграции, типизированный SQL) — важнее `sqflite`, потому что календарь и списки реактивны.
- **Состояние**: `riverpod` + `go_router`.
- **Уведомления**: `flutter_local_notifications` + `timezone` (на Android — точные будильники, на iOS — UNUserNotificationCenter).
- **Календарь**: `table_calendar` (или своя сетка, если упрёмся в кастомизацию).
- **Графики**: `fl_chart` (кривая брожения, кривая перегонки).
- **Прочее**: `intl` (RU-локаль, формат дат), `share_plus` + `file_picker` (бэкап/экспорт), `image_picker` (фото дегустаций), `http`/`dio` (интеграция с колонной — позже).
- **Сборка**: `flutter build appbundle` (Google Play), `flutter build apk` (RuStore/прямая установка), `flutter build ipa` (App Store, только на macOS); CI — GitHub Actions с macOS-раннером для iOS.

Правило: **никаких пакетов только под Android**, если у функции есть iOS-аналог. Всё, что платформенно-специфично, прячем за интерфейсом в `lib/platform/`.

Принципы: **оффлайн-первый** (всё локально, без аккаунта), данные экспортируются в JSON/CSV, никакой телеметрии.

## 7. Риски и ограничения

- **Сторы и алкогольная тематика**: Google Play, RuStore и App Store по-разному смотрят на контент про домашнее производство алкоголя. Требования: рейтинг 18+, формулировки «рецепты для домашнего приготовления», без призывов к продаже, без инструкций по обходу закона. Apple в этом плане строже всех — возможен отказ; запасной путь — RuStore + прямая установка. Проверять правила до подачи, а не после.
- **iOS без Mac**: собрать `.ipa` на этом хосте невозможно. Нужен либо Mac, либо CI с macOS-раннером (GitHub Actions). Разработка и тесты логики — общие, разница только в финальной сборке.
- **Точные будильники на Android 13+** требуют `SCHEDULE_EXACT_ALARM` и объяснения пользователю; иначе напоминания «плывут» — fallback на неточные + бейдж в приложении.
- **Данные пользователя**: рецепты и журнал — это годы записей, поэтому бэкап обязателен с первого релиза, а не «потом».
- **Объём контента** — самая дорогая часть: 100+ рецептов и справочников надо не выдумать, а собрать и вычитать. В MVP берём проверенный минимум, остальное — пачками.

## 9. Идеи после релиза (не в MVP)

### 9.1 Распознавание этикеток и упаковок (OCR → ингредиенты)

Сценарий: купил пакет сухих ингредиентов (смесь для настойки, солод, дрожжи, концентрат) — сфотографировал этикетку, приложение вытащило состав и добавило позиции в рецепт.

Как это делается **без ИИ и без интернета**:

- **ML Kit Text Recognition (on-device)** — `google_mlkit_text_recognition`, работает офлайн, бесплатно, поддерживает кириллицу, есть и на Android, и на iOS. Для этикеток этого достаточно: нужен только текст.
- Дальше — **разбор текста правилами**, не моделью: ищем строки состава, отделяем название от количества, нормализуем единицы (г/кг/мл/л/%), сопоставляем со справочником ингредиентов по словарю синонимов («сахар-песок», «сахарный песок», «сахар» → `sugar`).
- Пользователь видит распознанное, правит руками, подтверждает. Ничего не добавляется молча.

Где может понадобиться API (платный, по желанию):

- **Google Cloud Vision / Yandex Vision OCR** — если ML Kit не берёт сложную вёрстку, выцветший текст или язык не распознан. Тогда фото уходит на сервер — значит, нужна политика конфиденциальности и явное согласие.
- **LLM для разбора состава** (любая модель через API) — если хочется понимать «Е621, ароматизатор идентичный натуральному» и объяснять пользователю, что это. Это уже «умная» часть, делать после того, как заработает офлайн-разбор.

Порядок внедрения:

1. ML Kit OCR + ручное подтверждение распознанных строк (офлайн, бесплатно) — **основной путь**.
2. Словарь синонимов ингредиентов + автодополнение при вводе состава.
3. Опционально: облачный OCR как fallback для плохих фото (с явным согласием).
4. Опционально: LLM-разбор состава и подсказки по применению.

Отдельно: **распознавание фото продукта** (не текста) — определить по снимку, что это за настойка или бочка, — требует модели, обученной на своих данных; это не про этикетки и в план ближайших версий не входит.

Ограничения, которые надо помнить:

- Камера и чтение файлов — разрешения; на iOS нужен `NSCameraUsageDescription`, иначе ревью отклонит.
- Пакеты ML Kit тяжёлые: APK вырастет на 10–20 МБ. Поэтому — отдельным модулем после релиза, а не в MVP.
- Русские этикетки часто содержат состав мелким шрифтом и сокращения — ручная правка обязательна.
